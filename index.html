The Mendix application mental model

  • Domain model defines the business data and relationships.
  • Pages present data and provide user interactions.
  • Microflows and nanoflows implement logic in their respective execution contexts.
  • Workflows coordinate longer-running processes and human tasks.
  • Security controls who can access pages, entities, attributes, and records.
  • Integrations connect the app to external services, data sources, and devices.
  • Deployment and governance control how the app is released, operated, and maintained.

A scenario question often combines several areas. A user clicks Register; a microflow retrieves a Ticket, checks availability, validates rules, creates and commits a Registration, and refreshes the list. Security must also allow the action and the resulting data.

Recommended study strategy

  • Master topics 1–7 first: XPath, microflows, domain modeling, validation, pages, end-to-end logic.
  • For each topic learn: definition, why it is used, how it works, when to choose it, one common failure mode.
  • Explain your own app examples out loud. Trace data from a page action through logic and back to the UI.
  • Use the question bank to check understanding; explain why each answer is right.

Scenario-solving method

  • Extract requirement words: only, future, current user, related, required, unique, approved, before, after.
  • Identify entities, attributes, associations, and data types.
  • Choose the mechanism: XPath, validation, microflow, workflow, access rule, page widget, or integration.
  • Decide where the rule must be enforced so it cannot be bypassed.
  • Test valid, invalid, boundary, empty, duplicate, and unauthorized cases.

Constrain Your Data Using XPath

Essential

Learning goalRetrieve the correct objects and apply data-level access restrictions.

Key notes

  • XPath constrains objects retrieved from the database. It is not general-purpose SQL; it uses Mendix entity, attribute, association, and system-variable concepts.
  • Attribute constraint filters by an attribute: [Status = 'Open'].
  • Multiple bracketed constraints combine as AND: [Status = 'Open'][Priority > 2]. Use or when either may match; use parentheses to make combined logic clear.
  • Association constraint filters through a relationship: [Order_Customer = $Customer]. The association name and direction must match the model.
  • Use variables to compare against a current object or parameter. A variable such as $Customer is not interchangeable with a system variable.
  • System variables include [%CurrentUser%] and [%CurrentDateTime%] for dynamic constraints.
  • Enumeration constraints must use the correct qualified enumeration value, not arbitrary display text.
  • String functions such as contains or starts-with support text constraints. Watch case sensitivity and exact syntax for your Mendix version.
  • XPath is used in data source retrieves and entity access rules. Access-rule constraints limit which records a role can read or modify.
  • Filtering in a page widget is not a security boundary. Enforce security server-side with entity access and microflow permissions.
  • Constrain data as close to retrieval as possible; do not retrieve large lists and filter them later.

Worked scenarios

  • Library: My_Borrowings shows only the logged-in borrower's records. The record must relate to the Borrower account tied to the current user. Apply an access rule or secure retrieve condition, not only a page filter.
  • Future events: retrieve records related to a selected Course whose StartDate is later than the current date/time. Confirm the association path and the date comparison.
  • Empty retrieve: inspect the exact attribute, association direction, variable value, date boundary, and access rules. Test with known sample data.

Be able to answer in the exam

  • Difference between an attribute constraint and an association constraint.
  • Interpret AND/OR combinations and predict which records match.
  • Choose between a literal, a microflow variable, and a system variable.
  • Why page filtering does not replace entity access rules.
  • How an XPath access rule restricts a user to their own records.

Common misconceptionDo not assume a page filter protects data. A user may reach the data through another page, microflow, or integration unless server-side permissions are configured.

BonusExtra for the exam

  • Fully qualified names: [Module.Order_Customer = $Customer] and across associations [Module.Order_Customer/Module.Customer/Name = 'Ann'].
  • Empty checks: [Attr = empty], [Module.Assoc = empty], [Module.Assoc != empty].
  • Tokens go in quotes: [StartDate > '[%CurrentDateTime%]'], [System.owner = '[%CurrentUser%]']. Day/week/month/year helpers exist, e.g. [%BeginOfCurrentDay%] and [%EndOfCurrentDay%].
  • Microflow variable vs page token: in a microflow retrieve you write $Customer (no quotes). In a page widget XPath you cannot use microflow variables; use [%CurrentObject%] for the context object.
  • Other functions: not(...), contains(Name,'abc'), starts-with(Name,'A'). Keywords and / or are lowercase.
  • A user with several module roles gets the union of their entity access rules (rights add up).
  • Retrieve with XPath runs in the database. Retrieve everything and then Filter list in memory is slower and usually the wrong answer.

Building an Event App Using Microflows

Essential

Learning goalImplement server-side business logic and understand execution flow.

Key notes

  • A microflow is a sequence of activities executed on the server: retrieve, create, change, commit, delete, validate, call other logic, return values.
  • A microflow can receive parameters. The caller must provide an argument of the expected type (an Event parameter needs an Event object).
  • Variables hold objects, lists, or values created during execution. A variable is available only after its creation and within its valid scope/path.
  • Retrieve can read from the database using XPath, or through an association from an existing object.
  • Decision evaluates a Boolean expression and branches. Each outgoing path is a result (true/false). The condition must be complete and use variables in scope.
  • Loop processes each item in a list. The iterator variable is the current item, not the whole list.
  • Change Object changes values in memory. Commit persists them. They are separate operations.
  • Delete removes an object according to the application logic and security context.
  • A sub-microflow is reusable logic. Use clear parameter names, parameter types, and return types.
  • A before-commit event handler runs before an object is committed. It suits central rules that must apply whichever UI action saves the object.
  • An after-commit event handler runs after a successful commit; use it for follow-up behavior that depends on persistence.
  • Validation feedback communicates a business-rule failure. A failed validation path must not continue to Commit.
  • Error handling should consider missing objects, duplicate records, unavailable external services, and unexpected conditions.

Worked scenarios

  • Ticket registration: receive a Ticket; check capacity; decide whether places remain; validate; create a Registration; update capacity if the design needs it; commit the right objects; return a result or show feedback.
  • ProgramItem validation: before commit check required info and dependency rules. A field required only when another has a certain value is a Boolean rule.
  • Newsletter batch: retrieve a limited set of eligible records, loop, call a reusable send sub-microflow, record the result. Consider batch size and failure handling.
  • Missing parameter error: open the called microflow's parameter list and compare it with the caller's argument mapping.

Be able to answer in the exam

  • Trace a microflow from start to end and predict the path taken.
  • Distinguish parameter, local variable, iterator variable, and system variable.
  • Explain Retrieve, Change Object, Commit, Delete, Decision, Loop, and Call Microflow.
  • Choose between a microflow and an event handler for a business rule.
  • Explain why a change is not persisted until a commit occurs.
  • Recognize a variable-scope or missing-argument problem from an error message.

Common misconceptionA variable name used in an expression must exist on that execution path. A similarly named entity or attribute is not automatically a variable.

BonusExtra for the exam

  • Retrieve range: All, First, or Custom (amount + offset). First returns a single object that may be empty, so check $Obj != empty before reading attributes.
  • Splits: Exclusive split (Decision, Boolean or enumeration) vs Object type decision (inheritance split). A Merge joins paths again.
  • Activity error handling: Rollback (default), Custom with rollback, Custom without rollback, Continue. Inside a custom handler use $latestError; for REST also $latestHttpResponse.
  • Commit options: With events (handlers run) vs Without events (handlers skipped). Refresh in client updates what the user sees.
  • Rollback object reverts uncommitted changes to the database state (an object never committed is discarded).
  • Aggregate list gives Count, Sum, Average, Minimum, Maximum. List operations: Sort, Filter, Find, Union, Intersect, Subtract, Contains, Head, Tail.
  • Expressions: $Var/Attr, empty, if cond then a else b, and / or / not, string join with +. Use = to compare and != for not equal.
  • Before-commit handler returns Boolean. Returning false cancels the commit; true lets it continue. After-commit handlers run only after a successful commit.
  • Triggers: button, on-change, nanoflow call, scheduled event, task queue, page data source, entity event, published service, workflow.
  • Debugger: breakpoints, step over/into, variables pane, evaluate expression. Use Log message for server traces.

Expand Your Domain Modeling Skills

Essential

Learning goalRepresent business concepts and relationships accurately.

Key notes

  • An entity represents a business concept (Book, Borrower, Event, Registration).
  • An attribute stores a property. Pick the type by meaning: String, Boolean, Integer, Decimal for precise numbers, Date and time, Enumeration for fixed options.
  • An association connects objects: one-to-one, one-to-many, many-to-many.
  • One-to-many: one parent links to many children (one Borrower, many BorrowingRecords).
  • Many-to-many: both sides relate to many. If the relationship has its own attributes (registration date, status), use an intermediate entity.
  • An enumeration is a fixed list of values, ideal for states such as Draft, Submitted, Approved, Rejected.
  • Generalization lets a specialized entity inherit from a general one. Use it when entities truly share structure and behavior.
  • Persistable entities are stored in the database. Non-persistable entities are temporary: transient page data, filters, intermediate calculations.
  • Avoid duplicating data. Repeating a person's name in many records invites inconsistency; associate to the person.
  • Entity design affects security, retrieval, validation, and page context. A poor model complicates later logic.

Worked scenarios

  • Library: Book (title, author, category, availability), Borrower, BorrowingRecord linking both with BorrowDate, DueDate, status.
  • Event app: Event has many ProgramItems and many Registrations. A Ticket may belong to an Event and be used to create Registrations.
  • Use a non-persistable SearchCriteria entity for temporary page filters; a persistable one for data that must survive the session.
  • If Registration has its own status and date, model it as a business object, not a bare many-to-many link.

Be able to answer in the exam

  • Choose entity, attribute, association, or enumeration for a requirement.
  • Identify cardinality from a written scenario.
  • Explain when an intermediate entity is needed.
  • Distinguish persistable from non-persistable entities.
  • Explain generalization and when not to use it.

Common misconceptionAn association is not a text field containing another object's name. It is a real object relationship that supports navigation and integrity.

BonusExtra for the exam

  • Association types: Reference (one-to-many from the owner side) and Reference set (many-to-many). One-to-one is a reference with matching settings.
  • Owner: Default (only the "from" entity can set it) or Both. Ownership decides which object stores the link.
  • Delete behavior on an association: delete parent but keep children, delete parent and children, or delete parent only if it has no children (blocks deletion).
  • Attribute types to know: String (length), Integer (32-bit), Long (64-bit), Decimal, AutoNumber, Boolean, Date and time, Enumeration, Binary, Hashed string.
  • Attribute rules: Required, Unique, Range, Regular expression, Max length, each with its own error message. They are checked server-side at commit.
  • Calculated attributes are computed by a microflow on retrieval and are not stored. Indexes speed up frequent retrieves.
  • Non-persistable rule: a non-persistable entity may reference a persistable one, but a persistable entity cannot reference a non-persistable one.
  • System entities: System.User, System.FileDocument, System.Image. Optional system members: owner, changedBy, createdDate, changedDate.
  • Entity events: before/after Create, Commit, Delete, Rollback.

Practice Case: Explore Validation Patterns

Essential

Learning goalEnsure invalid data is rejected at the correct point with useful feedback.

Key notes

  • Validation checks whether data meets required conditions before it is accepted or committed.
  • Required-field validation checks a value is present. Business validation checks a rule such as DueDate later than BorrowDate.
  • Attribute-level rules validate one value. Object-level / microflow validation can consider several attributes and related objects.
  • A Boolean expression must evaluate to true or false, e.g. a valid grade: $Grade >= 0 and $Grade <= 100.
  • Use validation feedback to explain what is wrong and how to correct it.
  • Place validation before the commit when invalid data must not be persisted.
  • A before-commit handler centralizes validation that must apply whenever the object is committed.
  • Do not rely only on a page's required indicator; users may create or change data through other paths.
  • Test boundary values: minimum, maximum, just below, just above, empty, unexpected.
  • Validation asks is the data acceptable? Access control asks may this user do this? They solve different problems.

Worked scenarios

  • Learn Now: Grade is a Decimal. Validate its range and precision. If a learner must have attended before a grade is recorded, check that dependency as a business rule.
  • Course update: when a Course passing grade changes, update only future TrainingEvents of that Course if the requirement says so. Retrieve by association and date constraints.
  • Save sequence: user action → validate → if invalid, show feedback and stop → if valid, commit → refresh or navigate.

Be able to answer in the exam

  • Explain required-field versus business-rule validation.
  • Identify where validation belongs: attribute, microflow, or before-commit logic.
  • Predict what happens if validation fails.
  • Write a complete Boolean condition for a range or dependency.
  • Explain why a failed validation path must not reach Commit.

Common misconceptionA validation microflow does not automatically prevent saving if the caller ignores its result or continues to Commit. Make success and failure paths explicit.

BonusExtra for the exam

  • Validation feedback activity needs an object, a member (attribute), and a message. The message appears next to the input widget bound to that attribute.
  • Unique and other attribute rules are enforced at commit, server-side, whichever page or flow saves the object.
  • A before-commit handler that returns false cancels the commit, but the user sees nothing unless you also raise validation feedback or a message first.
  • Use lowercase and, or, not. && and || are not Mendix expression operators.
  • Boundary-test a range of 0–100 with: -1, 0, 100, 101, empty, and a value with too many decimals.

Create an App with Advanced Page Building

Essential

Learning goalBuild pages with the correct data source, context, and reusable structure.

Key notes

  • A page is a user-facing screen. It can use a layout, contain widgets, and receive parameters.
  • A layout provides reusable page structure (header, navigation, content region). A snippet is reusable UI content placed inside pages or layouts.
  • A Data View displays one object and gives object context to nested widgets.
  • A Data Grid displays a collection in rows and columns: sorting, filtering, selection, row actions.
  • A List View repeats items with a flexible layout. A Gallery suits visual collections.
  • A widget's data source can be database, association, microflow, or another supported source. It must return the expected object or list type.
  • A page parameter supplies the object or value needed when the page opens. If the page expects a Book, the navigation action must pass a Book.
  • Nested widgets use the context supplied by a parent Data View. If a widget cannot see the object, inspect the parent context and data source.
  • Conditional visibility and editability improve the UI but do not replace security.
  • Menu items and page access should match user roles.
  • Responsive design adapts to viewport sizes; do not assume a desktop layout works on mobile.

Worked scenarios

  • Books_Admin: grid of many books, then a detail page with the selected Book as its page parameter.
  • My_Borrowings: list filtered to the current borrower's records, also secured with entity access rules.
  • Edit form: a Data View whose source is the BorrowingRecord passed as a page parameter.
  • Missing object error: inspect the page's parameter definition and the action that opens it.

Be able to answer in the exam

  • Choose a Data View versus a Data Grid/List View.
  • Explain page parameter and data context.
  • Distinguish layout, page, and snippet.
  • Identify the data source for a one-object or many-object widget.
  • Explain why hiding a widget is not the same as restricting access.

Common misconceptionA page that requires an object parameter must be opened with the correct object. A correct page can still fail if the navigation action passes no argument.

BonusExtra for the exam

  • Snippet vs building block: a snippet is linked (edit once, every use updates). A building block is copied into the page (later edits do not propagate).
  • Common data sources: Context, Database, Association, Microflow, Nanoflow, Listen to widget.
  • Save / Cancel buttons: Save commits the object; Cancel rolls back uncommitted changes (a newly created object is discarded).
  • Page access: a page is opened only by users with an allowed module role. A page with no allowed roles is open to nobody.
  • Navigation profiles: responsive web, tablet, phone, native. Set a home page per user role.
  • Page-level XPath: use [%CurrentObject%] to filter by the context object, for instance a grid inside a Data View.
  • Performance: use paging and sensible page size; avoid loading very large lists into one grid.
  • Pop-up vs full page: pop-ups suit short edit forms; both receive parameters the same way.

Practice Case: Learn Now App Extended

Essential

Learning goalCombine modeling, XPath, microflows, validation, and UI behavior in one end-to-end case.

Key notes

  • Translate requirements into entities, attributes, associations, and enumerations.
  • Identify which objects must be retrieved and which constraints narrow the result.
  • Separate user interaction from business rules. A button starts a microflow, but the microflow enforces the important server-side rules.
  • Use sub-microflows for repeated checks; keep parameter and return types explicit.
  • Use loops only when several objects need processing; use single-object operations for one object.
  • Validate before commit and make sure invalid paths stop.
  • Use access rules to protect records by role or ownership.
  • Refresh the UI or return the correct object after changes.
  • Test positive, negative, boundary, and permission cases.

Worked scenarios

  • Grade rule: validate numeric range and precision.
  • Attendance rule: if a learner did not attend, decide whether a grade can be entered from the exact requirement.
  • Future event rule: update only events whose start time is after the current date/time; leave completed or active events alone if excluded.
  • Debugging rule: unknown variable → verify its creation activity and scope. Missing argument → inspect the parameter mapping.
  • Security rule: a user sees only records permitted by role and ownership.

Be able to answer in the exam

  • Explain the full data flow from page action to database and back.
  • Choose the right place for each rule: model, XPath, validation, microflow, access rule, or UI.
  • Identify likely causes of missing variable, missing parameter, empty retrieve, and uncommitted object errors.
  • Explain how to test with valid and invalid records.

Common misconceptionDo not solve every requirement in the page. Important business rules belong in server-side logic or security so they cannot be bypassed.

BonusExtra for the exam

  • Suggested model (illustrative): One Course has many TrainingEvents; each TrainingEvent has many Enrollments; each Enrollment belongs to one Learner. Enrollment holds Attended (Boolean), Grade (Decimal), Status (enumeration).
  • Trace to rehearse: Save click → microflow gets Enrollment → Decision on Attended → validate Grade range → Commit → Close page/refresh.
  • Future events XPath idea: [Module.TrainingEvent_Course = $Course and StartDate > '[%CurrentDateTime%]'].
  • Test matrix: valid grade, grade below 0, above 100, not attended with grade, past event untouched, learner A cannot see learner B.

Unlocking True Collaboration

Essential

Learning goalUnderstand team development, shared changes, and version control.

Key notes

  • Version control records project changes and supports collaboration among developers.
  • A development commit records model or project changes in the repository. It is not the same as committing a runtime object to the app database.
  • Updating brings shared changes into your working copy. Review incoming changes before continuing.
  • Conflicts occur when several developers change overlapping parts of the model. Resolve them by understanding the intended final behavior.
  • Branches isolate work or support parallel development depending on the repository workflow.
  • Domain model changes can affect pages, microflows, security, and integrations; coordinate them.
  • Use clear naming, regular updates, review, and testing to reduce integration problems.
  • Agree on ownership and communicate before changing shared entities, associations, or reusable components.

Worked scenarios

  • One developer renames an entity while another builds pages on it: changes may conflict or break references. Coordinate, integrate, run model validation, test affected flows.
  • A developer asks why a runtime object is not saved: a version-control commit will not help; inspect the microflow's database Commit activity.

Be able to answer in the exam

  • Differentiate repository commit from database commit.
  • Explain why teams update and resolve conflicts.
  • Recognize how shared model changes affect other parts of an app.

Common misconceptionDo not confuse development collaboration actions with runtime data operations.

BonusExtra for the exam

  • Team Server is Mendix's hosted Git repository for the app model. Studio Pro offers Commit, Update, Branch, Merge, Revert.
  • Good habits: update before you commit, commit small and often, write meaningful commit messages, merge feature branches back to the main line.
  • Developer Portal collaboration: backlog, sprints, stories, team roles, and the Feedback widget for user input.
  • Marketplace: reusable modules and widgets. Check version compatibility with your Studio Pro version before importing.

Importing and Exporting Your Data

High

Learning goalMove structured data safely between files and Mendix.

Key notes

  • Import brings external data in; export sends selected app data out.
  • Data mapping connects source columns to entity attributes. Names and types do not always match automatically.
  • Validate data types, required fields, enumeration values, dates, and numeric formats.
  • Handle duplicates deliberately: create, update, skip, or report.
  • Associations may require matching an external identifier to an existing Mendix object.
  • Large imports may need batch processing to control memory, time, and transaction size.
  • Provide meaningful error reporting: which row failed and why.
  • Export only authorized records and fields. Consider privacy and data minimization.
  • Test empty files, malformed rows, missing columns, duplicate identifiers, large datasets.

Worked scenarios

  • CSV import: columns BorrowerID, Name, ContactNumber. Map each to an attribute, validate required values, check whether BorrowerID exists, then create or update per the requirement.
  • Export: BorrowingRecords constrained to the current user's permitted records, excluding fields that are not needed.

Be able to answer in the exam

  • Explain mapping, validation, duplicates, associations, and error handling.
  • Why successful file parsing does not guarantee valid business data.
  • Privacy and access considerations for export.

Common misconceptionDo not import a relationship as unverified text when it should link to an existing object.

BonusExtra for the exam

  • Upsert pattern: retrieve by external ID; if empty create, else update. Add a Unique rule on the external ID.
  • Import/export mapping documents (XML/JSON) define how structures map to entities. Import mapping object handling: Create, Find, Ignore, plus a commit setting.
  • Batch pattern: retrieve a custom range (limit + offset), loop, commit the list, repeat. Keeps memory use low.
  • Marketplace helpers: Excel Importer and Excel Exporter modules for spreadsheet work.
  • Error log: write failures to a non-persistable or persistable ImportError list so users can fix specific rows.

External Entities and Catalog

High

Learning goalShare or consume data across Mendix apps and external systems.

Key notes

  • A local entity is owned and persisted by the app. An external entity represents data provided by an external source.
  • An external data source describes the connection and how data is accessed.
  • A consuming app uses data provided by another app or service. Know which system is the source of truth.
  • External entities expose only the operations the underlying service supports. Do not assume create, read, update, and delete all work.
  • A catalog helps teams discover and reuse published assets or data services in a governed ecosystem.
  • Mapping aligns external fields and data types with the consuming app.
  • Authentication, authorization, endpoint configuration, and network access are required for secure integration.
  • External dependencies can fail or be slow: handle timeouts, unavailable services, invalid responses, permission errors.
  • Avoid duplicating external data without a clear synchronization and ownership strategy.

Worked scenarios

  • An HR app owns employee data; a facilities app consumes it through a service. HR remains the source of truth; facilities must not silently build a second employee master.
  • If integration fails, inspect endpoint, credentials, service availability, mapping, and supported operations.

Be able to answer in the exam

  • Differentiate local and external entities.
  • Explain source-of-truth ownership.
  • Capabilities depend on the service.
  • Purpose of a catalog and secure integration.

Common misconceptionExternal entities are not local database entities with another label. Their behavior is set by the external service and integration.

BonusExtra for the exam

  • OData is the usual protocol: a published OData service exposes entities; a consumed OData service creates external entities. Query options include $filter, $top, $skip, $orderby, $select, $expand, $count.
  • REST and SOAP: published and consumed REST services use JSON/XML structures with import or export mappings. Call REST returns a status you should check.
  • HTTP status hints: 400 bad request, 401 unauthenticated, 403 not allowed, 404 not found, 500 server error.
  • Authentication options: basic, API key, OAuth/SSO. Secrets belong in constants or secure configuration, never hard-coded.
  • Catalog: registered services appear in the Catalog so other teams can find them. It is a discovery and governance aid, not the data store.

Implement a Design System

High

Learning goalBuild a consistent, accessible, reusable visual language.

Key notes

  • A design system is a shared set of principles, tokens, components, and usage patterns.
  • Design tokens are reusable values: colors, typography, spacing, borders, shadows.
  • Components are reusable interface elements: buttons, alerts, form patterns, navigation.
  • Patterns describe how components combine to solve recurring user tasks.
  • Consistency improves usability, maintainability, and speed of future development.
  • Accessibility includes readable contrast, clear labels, keyboard support, focus visibility, and appropriate feedback.
  • A theme provides global styling; reusable components and snippets apply the system consistently.
  • Document when to use each component so teams do not create inconsistent alternatives.

Worked scenarios

  • Define primary and secondary button styles once and reuse them. If the brand color changes, update the token or shared style, not every button.
  • Create a standard form pattern with labels, required indicators, validation messages, and spacing.

Be able to answer in the exam

  • Explain design system, token, component, and pattern.
  • Identify benefits beyond visual consistency.
  • Recognize accessibility as part of the design system.

Common misconceptionA design system is not just a color palette; it includes rules and reusable UI patterns.

BonusExtra for the exam

  • Atlas UI is Mendix's default design system and theme. It provides layouts, page templates, building blocks, and design properties (choose styles in Studio Pro without writing CSS).
  • WCAG contrast: at least 4.5:1 for normal text and 3:1 for large text (level AA).
  • POUR principles: Perceivable, Operable, Understandable, Robust.
  • Never rely on color alone to convey meaning (pair with icon or text).

Make Effective Widget Choices

High

Learning goalChoose widgets according to data shape and user task.

Key notes

  • Data View: one object, supplies context to child widgets.
  • Data Grid: tabular collections with sorting, filtering, selection, row actions.
  • List View: flexible repeated layouts. Gallery: visual card-style collections.
  • Input controls match the data type: date picker for date, checkbox for Boolean, dropdown for enumerations, reference selector for associations.
  • A reference selector lets the user choose a related object; it differs from typing text that merely resembles a name.
  • Charts should answer a specific analytical question, not decorate.
  • Consider data volume, responsiveness, accessibility, and task frequency.
  • Widget choice also depends on data source and context; the wrong data source breaks a visually correct widget.

Worked scenarios

  • Data Grid for a librarian's list of all BorrowingRecords; Data View to edit one selected record; dropdown for the BorrowingStatus enumeration.
  • Reference selector to link a BorrowingRecord to an existing Book or Borrower.

Be able to answer in the exam

  • Choose a widget for a single object versus a collection.
  • Explain when to use a reference selector.
  • Match input widgets to attribute types.
  • How data source and context affect a widget.

Common misconceptionChoose widgets by the task, not appearance alone.

BonusExtra for the exam

  • Data Grid 2 / Gallery are the modern pluggable widgets: column filters, sorting, selection, paging, column visibility.
  • Reference set selector or a Combobox widget handles many-to-many choices.
  • Widget families: classic (built-in) and pluggable (Marketplace or custom, built with React).
  • Template grid repeats a layout in a grid; Tab container and Accordion reduce clutter.
  • File / Image uploader widgets work with System.FileDocument / System.Image entities.

Build a Powerful Workflow

High

Learning goalCoordinate long-running processes with people and automation.

Key notes

Practice Case: Cash Flow

Practice

Learning goalApply modeling and business logic to a financial scenario.

Key notes

  • Cash inflow is money entering an account; outflow is money leaving.
  • Net cash flow for a period = total inflows − total outflows.
  • Closing balance = opening balance + inflows − outflows (subject to the case's accounting assumptions).
  • Use Decimal for money to avoid inappropriate floating-point representation.
  • Model transactions with amount, date, category, type, and account association.
  • Use enumerations or reference entities for controlled categories and statuses.
  • Validate required fields, permitted dates, positive amounts, and category rules.
  • Use XPath to filter by account, category, and date range.
  • Use access rules to restrict financial records to authorized users.
  • Test refunds, zero values, empty periods, date boundaries, duplicate transactions.

Worked scenarios

  • Calculation: opening 500; inflows 250; outflows 120; closing = 500 + 250 − 120 = 630. Use the right period and account.
  • March report: include the right start and end boundaries; do not include April transactions.

Be able to answer in the exam

  • Explain the cash-flow calculation and data model.
  • Choose suitable types and filters.
  • Explain validation, security, and boundary testing.

Common misconceptionDo not store money as formatted text. Store numeric values and format only for display.

BonusExtra for the exam

  • Half-open date range avoids boundary bugs: [TxnDate >= $Start and TxnDate < $NextStart] (for March: from 1 March up to, not including, 1 April).
  • Aggregate list (Sum) over the retrieved transactions gives inflow and outflow totals.
  • Second worked example: opening 1,000; inflows 400 + 250; outflows 150 + 90; net = 650 − 240 = 410; closing = 1,410.
  • Model idea: Account 1—* Transaction (Amount Decimal > 0, Date, Category enumeration, Type enumeration Inflow/Outflow). Use Type, not negative amounts, to keep rules simple.

BonusExam toolkit

Strategy, must-know facts, look-alike pairs, and common traps.

Exam-day strategy

  • Read the stem for restrictive words: only, must, best, first, strongest, secure, before, after. They decide between two plausible answers.
  • Prefer server-side enforcement over UI tricks for any security, validation, or business-rule question.
  • Eliminate absurd options first. Page titles, icons, colors, and captions are usually distractors for logic questions.
  • Trace step by step. For scenarios, write the flow: trigger → parameters → retrieve → decision → validate → commit → return.
  • Match the tool to the job: one object → Data View; many → Data Grid/List View; process with people → workflow; fixed values → enumeration.
  • Time-box. Skip and flag long scenarios; return after the quick wins.
  • Check your course: question count, time limit, and passing score depend on your provider. Confirm them in your course material.

Common traps

  • “Hide it on the page” is almost never the right security answer. Pick entity access rules with XPath.
  • “Change Object saves it” is wrong. Only Commit persists (or a Save action that commits).
  • “Validation microflow blocks saving automatically” is wrong. The failure path must not reach Commit.
  • Passing the wrong type to a microflow or page parameter. Match the exact entity.
  • Retrieve first without an empty check causes errors when nothing matches.
  • Many-to-many with attributes needs an intermediate entity.
  • Version-control commit ≠ database commit. Two different worlds.
  • Workflow ≠ long microflow. Use workflows for human tasks and process state.
  • External entity ≠ local entity. Capabilities come from the service; the external system owns the data.
  • More agent tools ≠ better agent. Least privilege and approval for sensitive actions.
  • Grounded AI answers can still be wrong. Human review and evaluation remain necessary.
  • Boundary dates: use >= start and < next start; do not double count or drop midnight.

25 facts to know cold

  1. XPath constraints in brackets combine as AND; use or for alternatives.
  2. Tokens like [%CurrentUser%] and [%CurrentDateTime%] are written in quotes in XPath.
  3. Page filters are not security; entity access rules with XPath are.
  4. Change Object edits in memory; Commit persists.
  5. Retrieve first returns one object that may be empty; check before use.
  6. A before-commit handler returning false cancels the commit.
  7. Validation failure paths must never reach Commit.
  8. Loop iterator = current item, not the list.
  9. Parameters must match the expected type, and pages needing an object must be given one.
  10. Many-to-many with its own data → intermediate entity.
  11. Non-persistable entities are temporary; persistable cannot reference them.
  12. Use Decimal for money; format only for display.
  13. Delete behavior can block deletion if children exist.
  14. Snippets are linked; building blocks are copies.
  15. Data View = one object; Data Grid/List View/Gallery = lists.
  16. Entity access, page access, and microflow access are all separate checks.
  17. Production security level for live apps; demo users only in development.
  18. Repository commit ≠ database commit; commit ≠ deployment.
  19. Workflows manage tasks and state over time; microflows run a sequence of logic.
  20. Import: map, validate, handle duplicates, report row errors, batch large files.
  21. External entities depend on the external service; the source system stays the source of truth.
  22. Atlas UI is the default design system; use design properties and Sass variables for consistent styling.
  23. Contrast ratio AA: 4.5:1 normal text, 3:1 large text.
